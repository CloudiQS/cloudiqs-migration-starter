# From SSB to Engagement — the playbook

You have a new migration case. This page is the order of work, from first contact to signed decision, and for each step: which SSB document you read, which kit file you fill, what you decide versus what your AI assistant drafts, and what the same step looked like for Acme in the workshop.

The workshop ran exactly these steps for one customer, in six modules. The method does not change for the next customer. The SSB documents, the customer facts, the requirements, the decisions and the approvals all do.

## The one idea

The SSB is a layered guidance pack. Each layer answers a different kind of question, and each step of an engagement leans on one layer more than the others:

| Layer | Answers | Leans on it most |
|---|---|---|
| 1-Pager | Should this pattern be considered, for which customer profile? | Qualify |
| Solution Design Document (SDD) | Which architecture, constraints, scope and anti-claims shape the pattern? | Map the estate, extract steering, design |
| Implementation guides | Which prerequisites, phases, checks and success criteria apply? | Discover, plan tasks, validate, decide |

The SSB never knows the customer's deadline, window, bandwidth, owners or approvals. Those come only from discovery. Every step below has both a guidance input and a customer input; the kit files exist to keep them apart and cited.

## Using it on your next workload migration case

The bundle in `ssb/` is the Workload Migration SSB's technical half: cloud-to-cloud transfer to AWS with DMS, MGN and DataSync. The steps above are the same for any case; what changes is how much of the guidance applies.

- **A source the guides list** (Azure SQL Database, Azure or GCE VMs, Azure Blob, Google Cloud SQL, Google Cloud Storage; see `ssb/evidence-index.md` §9) is `[SSB-DIRECT]` for that workload. Cite the passage and move on.
- **A source the guides do not list** (Acme's Azure Database for MySQL) is `[SSB-ADAPTED]`: borrow the nearest passage, name what was borrowed and what is missing, and verify on the real source before any number becomes a requirement.
- **A source outside the pattern** (on-premises VMware, SaaS applications, file shares on premises) is a gap. `sdd.md` — page 9 — `Anti-Claims and Common Misconceptions` says so; write the gap down in step 2 instead of stretching a passage to cover it. A confident "this SSB barely applies" is a valid step 0 result.
- **A different SSB** (for example Database Migration or Disaster Recovery) means redoing step 1 with that bundle: new manifest, new evidence index, new router corpus map. Steps 2–9 and every register stay as they are.

Your `ssb/` copy is frozen to the workshop's edition. For a real engagement, obtain the current SSB from Partner Ready Campaigns in AWS Partner Central under its access and redistribution terms, and rebuild step 1 from it. Service facts in the guides are edition-bound; check current AWS documentation before a guide's example setting becomes a design decision.

## What the kit deliberately leaves to you

The kit covers planning and evidence. It does not carry execution permissions, account policy, a change process or a cutover authority; the workshop's agent could run commands because it worked in a disposable lab account. The portable agent asks before every shell command for that reason. Where steps 7 and 8 touch a customer environment, your platform owner and the customer's change process decide who may run what, and the registers record that they did.
